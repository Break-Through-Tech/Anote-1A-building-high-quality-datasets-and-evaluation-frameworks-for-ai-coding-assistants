# Smoke run: Claude baseline vs Panacea, 5 MBPP tasks (2026-10-21)

**Pipe test only. Public tests, not comparable to final hidden-test scores.**

Purpose: check that the whole pipeline works end to end (load tasks, send a prompt to each arm, extract code, score it, write results). Five tasks is far too few to say which arm is better. Do not quote these pass rates as findings.

## Errors and failed runs

- No `Agent error:` from Panacea and no adapter failures (`failed_runs` = 0 for both).
- **mbpp-603 (both arms fail).**
  - Claude: `timeout` (10 s limit). Reading the code, it keeps the first element of the working list on every pass, so the `while numbers:` loop never ends. A real bug in the answer, not a harness problem.
  - Panacea: ran fine but returned the wrong list. I did not dig into why.
- **mbpp-622 (Claude passes, Panacea fails).** Output was cut off mid-way. See below. The function itself may have been correct; this score reflects the truncation and extraction, not necessarily code quality.

## Tokens and rough cost

- **Claude:** 3,619 output tokens in total (891, 1204, 540, 530, 454). The prompts were very short (557 characters in total), so input was a few hundred tokens.
- **Panacea:** the function does not report token usage. Output was 12,216 characters, which is roughly 3,500 tokens at about 3.5 characters per token (an estimate). It also makes at least two model calls per task (a tool call, then the answer) and sends tool definitions each time, so input is higher than Claude's, probably a few thousand tokens in total (not measured).
- **Rough cost:** assuming Sonnet-class list prices of about $3 per million input tokens and $15 per million output tokens (an assumption, not looked up; check Anthropic's pricing page), Claude was about $0.05 and Panacea about $0.06 to $0.09. Total well under $0.25. Check the Anthropic console for actual usage.

## Anything weird in extraction or scoring

1. **Truncated answer breaks extraction (mbpp-622, Panacea).** Panacea's output ran into the 1024-token cap in the middle of the example-usage block. The text had an opening code fence and no closing one. `extract_code` only recognizes a complete fenced block, so it fell back to the whole raw text, which starts with prose ("The workspace is empty, so I'll write..."), and that raised `SyntaxError`. This is the `max_tokens` 1024 vs 4096 mismatch showing up in practice. Worth fixing before any real comparison (for example, make `extract_code` accept an unterminated fence, and/or raise Panacea's limit). Not changed here.
2. **Both arms are chatty.** The raw MBPP prompt does not say "return only code", so both models returned code plus explanation and example usage (Claude about 450 to 1200 tokens per task). `extract_code` takes the first fenced block, which worked on 4 of 5 tasks for each arm. Longer answers also make truncation more likely for Panacea.
3. **Panacea always opens with a file check.** It says "the workspace is empty" and lists files first. That costs time and tokens and does nothing for self-contained tasks.
4. **Public tests only.** MBPP's `tests` field is now the public tests. The hidden tests are for final scoring and are not used here, so these scores are likely easier than the real ones.
5. **Panacea's temperature is 1.0 and this was one sample.** A rerun can give different results. Claude at temperature 0 is more repeatable but not guaranteed identical.
6. **Panacea token usage is not exposed**, so its cost is estimated, not measured.

## What this does and does not show

- The pipeline works end to end for both arms: loading, prompting, calling, extraction, scoring and saving all ran with no crashes.
- It does **not** show that Claude beats Panacea. With 5 tasks, one task is 20 points, and at least one of Panacea's extra failures is an output-length and extraction problem, not a code-quality one.
- Suggested before a real comparison: decide on temperature and `max_tokens` for Panacea, make code extraction robust to truncated and verbose answers, and use more tasks.
